## PAC extraction (no offset guessing)

Entry table lives at byte **2124**; entries are **2580 bytes** each; ids/names are
UTF-16 at +4 and +516. A stored offset **below 4 GiB can still be a truncated u32** —
the rule is: an image really sits at `stored + 0x100000000` if the file is >4 GiB AND
the image's own end/neighbors demand it. Practical disambiguation: if the naive read
does not start with `DHTB`, try the wrapped offset (that's how sml/teecfg/trustos
were recovered — `0x600d74dc` failed, `0x1600d74dc` gave valid DHTB images).

```python
TBL, ESZ = 2124, 2580
# walk entries; sizes/offsets at 1540 (<4I): nFileSize, nFileFlag, nCheckFlag, off
```

Useful entry ids in the S200162 PAC: `FDL` (fdl1-sign.bin), `FDL2`, `UBOOTLoader`
(u-boot-sign.bin — same bytes as the device's `uboot_a`), `SML`, `Teecfg`, `Trustos`.

## Hash pins for the generated bundle

The upstream runner (`Lenovo-TB328FU-Bootloader-Unlock-Root` repo) pins its author's
device dumps (`FDL_SHA=a9cf547c…`, `UBOOT_SHA=83e7039a…`, CURRENT_FULL sml `7ed64933…`).
Those pins describe the author's device, not the PAC-extracted images — the author's
`uboot_a` dump matched their pin, while the device captured here trims to the same
909188-byte image after `parse_image` and patches to the **identical confirmed cboot**
byte-for-byte. We therefore verify structure, not the author's hashes:

## Rebuild everything from scratch

```bash
# 1. extract inputs from the official PAC (tools/extract_pac.py)
# 2. prime fdl1:  wine gen_fdl1-dl.exe fdl1-sign.bin   → fdl1-dl.bin
# 3. python3 tools/build_bundle.py        (regenerates bundle/)
# 4. verify with bundle/built-report.json against the table above
```
